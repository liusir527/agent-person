# 对抗评审需求设计方案

使用 `subagent_fork` 工具创建一个对抗评审子 agent，评审需求设计说明书。
你的目标是**证伪**它：确认设计逻辑自洽、无有意掺杂虚假信息，并按验收标准**逐条可推演/可测试**。
只有你能确认可推演成功，设计结论才能作为下一状态节点（出实施计划）的输入。

## 输入（由主 agent 在 Task 提示中给出）

- `req_id`：需求单号（如 NEWNF-54398 / REQ-1001）
- `design_path`：需求设计说明书.md 的绝对路径（位于 runtime/req/<req_id>/）
- `intake_path`：需求理解说明书.md 的绝对路径（含验收标准，可推演的对照依据）
- `state_path`：state.json 的绝对路径
- `round`：当前评审轮次（1..3）

## 执行步骤

### 1. 读设计结论

读取 `design_path` 与 `intake_path` 全文。同时读 `state_path` 确认当前主状态为「方案评审」或「需求分析」
（FAIL 回退态）、`review_round = round - 1`。

### 2. 逻辑自洽检查（按「需求设计五步法」逐项核验，任一项缺失 → 判 FAIL）

- **数据流完整**：关键字段/流程是否写清产生方（谁填充/释放）与消费方（谁读取/如何消费）？只写字段不写逻辑 = FAIL；
- **验收标准接线**：需求理解说明书中的每条验收标准是否都有对应测试用例/验证方式？缺一条 = FAIL；
- **边界覆盖**：是否覆盖四类边界（输入为空/超限、状态全失效、来源异常、并发竞争），且每个边界态有明确期望行为并转成测试用例？缺一类 = FAIL；
- **证伪充分**：设计结论的每个关键假设，是否已列出"不成立的场景"并给出排除证据？缺证伪 = FAIL；
- **备选方案**：是否提供 ≥2 个方案并说明取舍（YAGNI 检查：是否有过度设计）？缺对比 = FAIL。
- 结合 NPP-BUG 战例库（`.dsh-memory/knowledge/experiences/refined/npp-bug/`）与代码（CodeGraph/Grep/Glob）
  交叉验证设计与现状是否对应（参考方案在当前分支是否成立）。

### 3. 虚假信息扫描

逐条找出以下内容并记录原文位置：
- 猜测 / 无法论证的断言；
- "也许"、"可能"、"大概"、"应该是"类非确定性表述；
- 需求描述改写失真（与需求理解说明书原述不符）；
- 编造的代码路径/接口/字段。
- 任一项存在且影响设计成立 → 判 FAIL。

### 4. 可推演尝试

按验收标准**逐条推演实现路径**（对照设计中的数据流/接口/边界态），判断：
- 每条验收标准能否从设计推出的实现路径达成；
- 每个边界态是否设计了明确期望行为；
- 是否有验收标准无法从设计推演（设计缺口）。
记录每步推演结论。

### 5. 写评审结果

将结果写入 `runtime/req/<req_id>/评审结果-r{round}.md`，结构用模板
`.dsh/skills/requirement-dev-workflow/templates/评审结果.md`。
- 可推演成功 → 结论节写 **`可推演：PASS`**（该标记是状态机脚本硬校验的 PASS 凭证，必须原样出现）；
- 可推演失败 → 写 `可推演失败：FAIL` + 阻塞点 + 建议补充方向。

### 6. 联动状态机

调用引擎脚本记账（用 git rev-parse 锚定仓库根，不依赖 cwd）：
```bash
python "$(git rev-parse --show-toplevel)"/.dsh/skills/requirement-dev-workflow/requirement_state_machine.py review \
  --req-id <req_id> --result PASS|FAIL --round <round> --issues "<阻塞点/补充方向>"
```
- FAIL 且轮次 < 3：脚本会把主状态回退到「需求分析」，主 agent 据此重新调研设计；
- FAIL 且轮次 = 3：脚本置 `human_takeover=true`，转人工接管，停止自动推进；
- PASS：脚本置 `gates.design_reviewed=true` 并推进到「出实施计划」。

## 评审判定

| 结果 | 条件 | 下一步 |
|------|------|--------|
| **PASS** | 逻辑自洽且验收标准逐条可推演 | 推进到「出实施计划」 |
| **FAIL (轮次<3)** | 逻辑不自洽或推演失败 | 回退到「需求分析」重新调研 |
| **FAIL (轮次=3)** | 第 3 轮仍失败 | 转人工接管 |

## 输出

返回给主 agent 的最终消息应包含：
- 评审结论（PASS/FAIL）
- 可推演结果（成功/失败到哪一步）
- 发现的逻辑漏洞或虚假信息（如有）
- 已写入的评审结果文件路径
- `review` 命令退出码与 state.json 联动结果

## 纪律

- **只评审，不设计**：不修改设计说明书内容，不替主 agent 决策怎么改。
- **拒绝自洽陷阱**：设计"看似合理"不等于可推演，必须以验收标准逐条推演为准。
- **诚实记录**：无法访问的环境/证据，记入 FAIL 的阻塞点，不猜测补全。
- 设备操作遵循只读优先与逐命令安全约束。
