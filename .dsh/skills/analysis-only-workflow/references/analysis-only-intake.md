# 取证与假设（lite 版）

> 对齐 bug-fix-workflow 的 BUG 分析五步法，但**不需要设备/编译机**，所有证据来自代码、日志、用户描述。

## 1. 取证五步法（lite 版）

### 1.1 收集三类证据

1. **现象证据**：用户描述 / 日志片段 / 截图说明 / 报错堆栈。
2. **代码证据**：通过 grep / CodeGraph 定位关键符号、调用链、产生方 / 消费方。
3. **历史证据**（如有）：git blame 看最近变更、git log 看历史 fix。

### 1.2 画数据流（必做）

`谁产生 → 谁消费 → 怎么消费 → 空/边界怎么办`

字段只是结果，逻辑才是真相；找不到产生方或消费方 = 没理解问题。

### 1.3 列假设与证伪

| 优先级 | 假设 | 验证方式 | 证伪条件 |
|--------|------|----------|----------|
| P0 | | | |
| P1 | | | |

主动列"这个假设在哪些场景不成立"，列不出来 = 没理解透。

### 1.4 边界态三类（必填）

- ①数据为空 / 被释放
- ②首选不在候选列表
- ③来源异常（查不到 / 字段缺失）

每个边界态必须转成自测用例。

### 1.5 写进分析产物

落到 `<项目根>/runtime/analysis/<slug>/问题分析结论.md`，**字段缺失会被对抗审查 FAIL**。

## 2. lite 流程的取证工具限制

- ✅ CodeGraph / grep / Read / git log / git blame
- ✅ 用户提供的日志/截图（用户主动粘贴或描述）
- ❌ 不下载附件、不 OCR、不开浏览器
- ❌ 不上设备取 vppctl / SSH（除非用户明确要求）
- ❌ 不上编译机取编译日志

## 3. 何时升级到 bug-fix-workflow

如果取证过程中发现：

- 需要在真实设备上 SSH 取 vppctl 输出 → 升级
- 需要上编译机 nsbuild-git 编译 → 升级
- 改动需走 PR / 工单 → 升级
- 用户主动提供 BUG 单号 → 升级

升级方式：把 `<slug>` 对应的产物（问题分析结论.md 等）原地保留，**在 bug-fix-workflow 里新建一条 `init --bug-id NEWNF-XXX`** 重新走主状态机，**复制** 产物过去，避免重复取证。
