# 修复与验证

在已知可能根因或代码区域后使用本阶段。

## 编码默认要求

- 匹配周边代码风格、命名、错误处理、日志方式和线程假设。
- 除非根因要求修改共享抽象，否则保持改动小而局部。
- 注意时序、转发路径、API 合约、所有权/生命周期、锁和线程模型。
- 保留工作区中的用户改动。

## 影响范围评估

编辑前或编辑后立即评估：

- 直接调用方和被调用方
- 能到达该代码的配置路径
- 数据结构、所有权或生命周期变化
- 并发和时序影响
- 转发路径和性能风险
- ABI/API 兼容性
- 覆盖改动行为的测试或手工验证

可用时使用 CodeGraph 或 GitNexus impact-analysis。

## 验证范围

选择最小但可信的验证集合：

- 局部逻辑的单元测试或组件测试
- API/转发行为的集成测试
- 触达模块的构建或编译检查
- 设备复现或只读运行态确认
- 相邻模式、分支或配置变体的回归检查

测试无法运行时，说明原因，并给出最接近的手工验证路径。

## 完成标准

满足以下条件后再交付：

- 根因和行为变化能够解释清楚
- 影响范围已说明
- 已运行测试/手工检查，或明确说明阻塞原因
- 剩余风险已显式列出
