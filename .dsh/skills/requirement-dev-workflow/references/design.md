# 需求分析与设计

需求理解获确认后使用本阶段。目标是产出**需求设计说明书.md**——证明"怎么建"，而非"为什么坏"。

## 需求设计五步法（需求设计说明书.md 必填，评审 FAIL 项同 bug-fix）

1. **先画数据流再设计**：新字段/新流程同样要写 `谁产生 → 谁消费 → 怎么消费 → 空/边界怎么办`。
   字段只是结果，逻辑才是真相；找不到产生方或消费方 = 没理解需求。
2. **参考方案只作线索不作答案**：借鉴旧需求/同模块实现必须验证在当前分支成立。有参考 ≠ 有答案。
3. **强制自我证伪**：设计结论后主动列出"这个设计在哪些场景不成立"。列不出来 = 没想透，不许进实施计划。
4. **必须追到边界态**：至少四类——输入为空/超限、状态全失效、来源异常、并发竞争；给每个边界态明确
   期望行为，并**每个边界态必须转成测试用例**（对应验收标准→测试用例的接线）。
5. **推进前提**：全门禁一关不能跳——设计结论须经对抗评审（可推演）才进实施计划。

## 设计产物结构（需求设计说明书.md）

1. **需求回顾**：一句话指向审查通过的需求理解说明书（含验收标准），不重复整段。
2. **现状调研**：现有代码路径/数据结构/数据流（CodeGraph 支撑），确认本次改动落点。
3. **方案设计**：
   - 数据流（产生方 → 消费方 → 消费方式 → 空/边界行为）；
   - 接口设计（函数签名/`*.api` 字段/biapi 消息，涉及 `.api` 改动标注走 vpp-api-sync）；
   - 数据结构与生命周期（所有权/释放/锁/线程模型）；
   - 边界态清单（每项 → 测试用例）；
   - 证伪清单（设计不成立的场景 → 是否排除 → 排除证据）。
4. **备选方案对比（≥2）**：方案A/B 优缺点 + 为何选它（结构清晰/可复用/兼容性/是否已有同类实现）。
5. **影响范围评估**：
   - 直接调用方/被调用方；
   - 配置链路 / 数据结构 / 所有权 / 生命周期；
   - 并发与时序影响；
   - 转发路径 / 性能风险；
   - ABI/API 兼容性（`*.api` 改动 → biapi 消息格式变化，vpp-agent 交接）；
   - 回滚成本。
6. **验收标准接线**：需求理解说明书中的每条验收标准 → 对应的测试用例/验证方式。

## 影响范围评估（编辑前或编辑后立即评估）

- 直接调用方和被调用方
- 能到达该代码的配置路径
- 数据结构、所有权或生命周期变化
- 并发和时序影响
- 转发路径和性能风险
- ABI/API 兼容性
- 覆盖改动行为的测试或手工验证

可用时使用 CodeGraph 或 GitNexus impact-analysis。

## 评审入口

设计产物齐 → 主状态推进到「方案评审」→ 派 `design-reviewer` 对抗评审（按验收标准可推演/可测试）。
FAIL 且轮次<3 回本阶段重新调研；第 3 轮 FAIL 转人工接管。
