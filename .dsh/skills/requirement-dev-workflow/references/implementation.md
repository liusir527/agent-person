# 需求实现（编码）

实施计划经用户确认后使用本阶段。目标：按计划实现，走 TDD + 代码审查闭环 + 编译验证。

## 编码默认要求

- 匹配周边代码风格、命名、错误处理、日志方式和线程假设（C/VPP 项目尤其注意 vpp 的线程模型与内存所有权）。
- 除非需求要求修改共享抽象，否则保持改动小而局部。
- 注意时序、转发路径、API 合约、所有权/生命周期、锁和线程模型。
- 保留工作区中的用户改动。

## TDD 铁律（吸收 superpower-TDD）

- **无失败测试不写生产代码**：每个新增函数/行为先写失败测试（红）→ 最小实现（绿）→ 重构；
- 验收标准（需求理解说明书）必须先转成测试用例，测试先行才有判据；
- 测试先写后补（先实现后补测试）等于没测——你从未看到它失败，无法证明它能捕获缺陷；
- 无框架时用最小复现脚本，能本地闭环的先本地闭环。

## 受限环境测试（常态策略，不是应急）

编码阶段的验证同样受环境约束：
- 能本地闭环的（单测/逻辑/边界态）先闭环；
- 受限环境运行态验证（VPP 启动、模块 show、构造报文触发路径）按需进行；
- 不能测的显式登记为交接项，见 `testing.md`。

## 影响范围评估

编辑前或编辑后立即评估：

- 直接调用方和被调用方
- 能到达该代码的配置路径
- 数据结构、所有权或生命周期变化
- 并发和时序影响
- 转发路径和性能风险
- ABI/API 兼容性（`*.api` 改动 → vpp-api-sync 暂存 api.json）
- 覆盖改动行为的测试或手工验证

## 验证范围

选择最小但可信的验证集合：

- 局部逻辑的单元测试或组件测试（TDD 红绿）
- API/转发行为的集成测试
- 触达模块的构建或编译检查
- 设备复现或只读运行态确认
- 相邻模式、分支或配置变体的回归检查

测试无法运行时，说明原因，并给出最接近的手工验证路径（或登记为交接项）。

## 代码审查闭环（进入「测试验证」前的强制门禁）

- 编码落盘后先走 `file-review`（落盘通用审查，≤3 轮），再派 `code-reviewer`（语义审查五维：
  正确性/最小性/风格一致/影响面/编译可达；P0/P1 阻塞 PASS，P2 记录）；
- PASS 落盘 `代码审查报告-rN.md`（结论行 `审查通过：PASS`）→ `gate --flag code_reviewed --evidence <报告>`；
- FAIL 且轮次<3 回「修改」修正后复审；第 3 轮 FAIL 转人工接管；
- 接收反馈：先验证再实施，禁止表演式认同，外部评审意见须对照代码核实（见 `code-review.md`）。

## 编译验证（证据型门禁）

- 编码结束时必须编译验证，通过后执行
  `gate --flag build_passed --value true --evidence <编译日志路径>`（无证据文件拒绝置位）；
- 涉及 `*.api` 改动：编译通过后自动执行 `vpp-api-sync` 暂存 api.json（见 `task-boundary.md` §2）；
- `code_reviewed` + `build_passed` 都置位后才能 `advance --to 测试验证`。

## 完成标准

满足以下条件后再交付：

- 每条验收标准都有对应实现 + 测试接线
- 影响范围已说明
- 已运行测试/手工检查，或明确登记交接项
- 剩余风险已显式列出
