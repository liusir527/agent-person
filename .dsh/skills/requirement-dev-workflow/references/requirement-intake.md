# 需求理解与澄清

在处理需求单/PRD/口头需求时使用本阶段。目标是**理解目标 + 拆解范围 + 定验收标准**，
与 bug-fix 的"找根因"不同——需求是"建什么"的问题。

## 输入形态

| 形态 | 动作 |
|------|------|
| 需求单/JIRA feature | 读取需求描述、验收条件、影响版本、设备型号、分支、附件和评论 |
| PRD/设计文档 | 通读，提取功能点与约束，与代码现状对照 |
| 口头需求 | 整理为最小可用需求描述：目标 / 范围 / 约束 / 验收 |

## 需求澄清清单（需求理解说明书.md 必填）

1. **需求原始描述**（原样引用，勿改写）；影响版本/设备型号/分支；
2. **归属层判断**：WEB / AGENT / VPP（npp）——配置管理类需求归 AGENT/WEB；VPP 需求聚焦转发/选路/
   运行态逻辑 + 经 biapi 暴露或接收的字段；确需跨层先定"本次动哪层"，跨层另走分层 plan；
3. **范围界定**：in-scope / out-of-scope 显式列出；
4. **需求拆解**：拆成可独立交付的子任务（story），标注依赖顺序；
5. **验收标准**：每条可量化/可判定（命令输出、字段值、行为）——这是后续评审与测试的唯一标尺，
   **每条验收标准必须能转成测试用例**；
6. **待确认项**：信息不足时聚焦反向提问，不泛问。

## 反向提问

- 需求单信息不完整时，提出聚焦的反向问题，避免泛泛要求用户补充。
- 一次问一个问题；能用选择题就不用开放题。
- 只有缺失信息会阻塞安全推进时才提问。

## 需求分类定级（吸收 superpower-brainstorming）

澄清首步先分类，决定流程深度（审批关卡不放宽，产出物随类别伸缩）：
- **spike（可行性）**：只验证"能不能做"，产出是答案而非代码；
- **bounded（本仓库小改动）**：可简化产物（对话级设计），但需求理解+验收标准仍须用户确认；
- **architectural（跨层/新子系统）**：走全门禁 + 完整设计文档；
- **棘轮单向**：中途发现隐藏复杂度只升级路径（bounded→architectural），不允许降级。

## 假设循环

维护按优先级排列的假设列表：

- 假设
- 支持证据
- 反证
- 下一步最低成本检查
- 所需工具或权限

## 计划门禁

满足以下任一条件前，不进入需求分析/设计：

- 验收标准已与需求方对齐（gates.requirement_confirmed）
- 范围（in/out scope）与归属层已明确
- 用户明确要求先出试探性方案

仍不确定时，先输出澄清结论，再进入设计。
