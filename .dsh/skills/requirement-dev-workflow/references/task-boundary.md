# 需求边界与防扩散约束（每次开工必读）

> 本工作流聚焦 **VPP（npp）层需求实现**；配置管理类需求属于 AGENT/WEB。开工前必须明确：本次只改哪个
> 仓库/工作区、需求属于哪一层、取证与停止条件。违反边界即为扩散，开工即回退。

## 1. 工作区边界（硬约束）

- 本次任务只允许修改 **用户指定的仓库与工作区**（如 npp worktree），其余一律只读。
- 禁止为其他仓库创建 worktree / 分支 / 提交（包括 WEB、AGENT、vpp-agent 等）。
- 确需跨层改动时，先说明理由等用户确认，不自行展开。

## 2. 分层架构认知（决定"需求属于哪一层"）

| 层 | 职责 | 常见需求形态 |
|---|---|---|
| WEB | 配置展示 / 下发 / 简单状态读取 | 界面、字段、下发参数 |
| AGENT | biapi 封装 / 配置中转 / 数据搬运 | 字段透传、消息格式、api 同步 |
| VPP（npp） | 转发逻辑 / 选路 / 运行态数据 | 转发行为、选路结果、运行态字段 |

判断顺序：
1. **配置管理类需求（新增配置项/下发链路）→ 属于 AGENT/WEB**，通常不作为 VPP 需求；VPP 只作配置消费方
   （经 biapi 接收）或数据产生方（经 biapi 上报）。
2. **转发/选路/运行态需求 → 优先在 VPP 层闭环**：先确认 VPP 侧是否已有数据或逻辑（vppctl/CLI/show），
   缺字段才考虑 biapi 上报链路。
3. 涉及 `*.api` 文件改动 → 编译通过后由本工作流**自动**执行 `vpp-api-sync` 暂存 api.json（约定动作，
   不需用户触发）。暂存完成后必须 `--expect-field <新字段>` 校验通过且本地 `runtime/<SESS>/<模块>.api.json`
   真实落盘（grep 命中新字段）才允许声称"已移交"；检测失败时用 `--api-file/--local-dir/--remote-worktree-name/
   --sess/--expect-field` 显式重试至成功。
4. 涉及 `*.api` 改动时上机验证**退化为冒烟验证**（npp 启动 + 基础命令可用）——这是常态策略，不是应急；
   全量验证属交接项（vpp-agent 同步 api.json 后由 WEB 侧回归）。

## 3. 取证约束（证据够用为止）

- 不下载附件、不开浏览器、不做 OCR。附件/截图不可读时，用文字描述现象请用户补充，不要绕路取证。
- 取证优先用设备只读命令（vppctl / CLI / show）确认 VPP 运行态，而不是翻上层代码。
- 远程命令必须用 ssh-tools / gdb-tools 等专用 skill，不自行拼凑。
- **受限环境取证**：无完整联调环境时，VPP 单机运行态即可满足大部分取证；缺 WEB/AGENT 链路证据时，
  在测试记录.md 中登记为交接项，不得靠猜补全。

## 4. 停止条件（每步自问）

> **这条信息会改变设计方案吗？不会就立即停止该方向。**

- 探索性工具（worktree 派生、文件系统逐层翻找、跨仓库 grep）占用的上下文不算进度。
- 每完成一个取证/探索动作，输出一句"结论：X；若此结论为假，方案是否受影响"，写不进这句话就停。

## 6. 与需求设计五步法的关系

五步法管"理解深度"（数据流、证伪、边界态）；本文件管"探索范围"（只在本层、只到够用为止）。
两者独立：即使还在需求澄清阶段，范围约束也立即生效。
