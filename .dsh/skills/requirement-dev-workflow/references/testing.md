# 受限环境测试策略（测试验证 主状态）

> **常态策略，不是应急手段**：VPP 层需求测试常无完整三方联调环境（无 WEB/AGENT/VPP），
> 只能在受限环境验证。核心原则：**能测的必须测，不能测的显式列为交接项，禁止用"环境受限"当不测试的借口。**

## 环境分层与测试边界

| 层 | 可测项 | 不可测/受限项 |
|---|---|---|
| 编译层（编译机） | 编译通过、语法/ABI 可达、`*.api` 生成 api.json | — |
| VPP 运行态（受限设备/单机） | npp 服务启动、`vppctl`/CLI/show 命令、运行态字段、转发/选路行为（构造报文/CLI 操作）、模块逻辑 | 经 WEB/AGENT 的配置下发全链路 |
| 完整环境（WEB+AGENT+VPP） | 配置下发→VPP 生效→界面显示 端到端 | 通常不可用 |

## 测试执行策略（按优先级）

1. **单测/逻辑验证**（本地可跑）：新增函数/模块用 C 单测（项目实际测试框架）验证逻辑与边界态
   （设计五步法四类边界态转用例）；无框架时用最小复现脚本，能本地闭环的先闭环；
2. **受限环境运行态验证**：VPP 单机启动 + 模块 show 命令核对运行态字段；构造报文/CLI 触发转发/选路
   路径核对行为；
3. **冒烟退化**：涉及 `*.api` 改动 → 上机验证退化为冒烟（npp 启动 + 基础命令：`systemctl is-active
   pss-npp`、`vppctl show version`、模块 show 命令）；biapi 变更后 vpp-agent 未同步时无法经 WEB/AGENT
   下发，全量验证属交接项；
4. **人机协作**：配置类验证由 agent 先出 `测试方案.md`（测试场景、步骤、命令、预期结果、所需配置），
   用户在（受限或完整）环境按方案配置（WEB / ssh），agent **不代行配置**；用户完成后 agent 按方案执行
   检查、比对预期、把结果记录到 `测试记录.md`（记录谁执行、实际结果、与预期的差异）；
5. **交接项显式化**：凡因环境受限无法验证的用例，必须在 `测试记录.md` 中列为「交接项」
   （谁 / 在哪个环境 / 何时验证），由用户在完整环境补验后 `confirm test_passed` 或单独确认交接完成。

## 验收判定规则（test_passed 置位条件）

- 受限环境下**能测的用例**：必须全部跑过——这是 `test_passed` 的硬性组成部分；
- **不能测的用例**：必须显式列「交接项」+ 明确责任人，禁止悄悄降级为"没测"；
- `test_passed` = 受限环境可测项全过 + 交接项已登记（完整环境验证可延后到交付后由用户/测试完成，
  属交付上线后的回归项）。

## 人机协作细则

1. agent 先输出 **测试方案.md**（测试场景、步骤、命令、预期结果、所需配置），提交给用户；
2. 由用户按方案在设备上完成配置（WEB / ssh），agent 不代行配置；
3. 用户完成后，agent 按方案执行检查命令、比对预期、把结果记录到测试记录.md
   （记录谁执行、实际结果、与预期的差异）；
4. 配置可能带来副作用（如重启服务、改变转发行为）时在方案中明示，由用户确认后执行。

## 完成标准

- 所有可测用例有 PASS/FAIL 结果（FAIL 用例须有修复或明确理由）；
- 交接项清单完整（谁 / 环境 / 时机 / 关联验收标准）；
- 已转人工验收（test_handed），人工验收通过（test_passed）后推进到「交付上线」。
