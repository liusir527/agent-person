## 一、设计哲学

### 1.1 五大原则（保留）

| 原则 | 说明 |
| :------------- | :------------------------------------------------------ |
| **明文真源** | 所有知识只存于 `.md` 文件，人类可读写，Git 可版本管理 |
| **索引可重建** | SQLite 索引是 `.md` 文件的缓存视图，随时可删、可重建 |
| **零模型依赖** | 不依赖 embedding / LLM，所有检索基于关键词 + 结构化字段 |
| **指纹去重** | 用确定性哈希（SHA-256）识别重复经验，避免知识库膨胀 |
| **跨环境迁移** | 整个目录 `git clone` 即恢复，无需任何外部服务 |

**v2 新增一条约束（对零模型依赖的补充说明）**：

> **中文检索需要确定性分词**。SQLite FTS5 内置的 `unicode61` tokenizer 对连续书写的中文字符串**不做词切分**（实测：正文 `容器内部无法访问宿主机` 被当作单个 token，搜索 `容器` 命中为 0）。v2 通过在**写入索引前**用 jieba 对中文做确定性切词（词间插入空格）解决。jieba 是纯本地、确定性、无模型的词法库，不违反零模型依赖原则。

### 4.1 SQLite 表结构（v2 重写）

```sql
PRAGMA journal_mode = WAL;               -- v2: 并发读写（--watch 与查询并存）

-- 主表：存储结构化元数据
CREATE TABLE experiences (
    id TEXT PRIMARY KEY,
    file_path TEXT UNIQUE NOT NULL,      -- 相对根目录的路径

    category TEXT,
    project TEXT,

    updated_at INTEGER                   -- 来自 Frontmatter

-- 【v2】tags 关联表（替代逗号拼接 + LIKE，消除子串误配）
CREATE TABLE experience_tags (
    exp_id TEXT NOT NULL REFERENCES experiences(id) ON DELETE CASCADE,
    tag TEXT NOT NULL,
    PRIMARY KEY (exp_id, tag)

CREATE INDEX idx_tags_tag ON experience_tags(tag);

-- 【v2】FTS5：content 存"jieba 预分词后的文本"；doc_id 直接用主表 id

CREATE VIRTUAL TABLE experiences_fts USING fts5(
    content,
    tokenize = 'porter unicode61'       -- 只负责英文词干；中文已在外层分词成空格串

-- 【v2】关联：FTS rowid ↔ 经验 id（小而正确的映射，随事务一起维护）
CREATE TABLE fts_map (
    id TEXT PRIMARY KEY REFERENCES experiences(id) ON DELETE CASCADE,
    fts_rowid INTEGER UNIQUE NOT NULL
);

-- 索引：加速查询
CREATE INDEX idx_experiences_severity ON experiences(severity);
CREATE INDEX idx_experiences_project ON experiences(project);
CREATE INDEX idx_experiences_occurrence ON experiences(occurrence DESC);
```

### 4.2 中文预分词（v2 新增，写入 FTS 前的必经步骤）

```python
# scripts/tokenizer.py
import jieba

# jieba 保持确定性：固定词典 + 关闭 HMM 以稳定切分
jieba.setLogLevel(jieba.logging.WARN)

def segment_for_fts(text: str) -> str:
    """中文预分词：中文字符之间插空格，英文/数字保持原样。
    unicode61 会把连续的 CJK 字符当成一个 token，导致中文无法按词检索，
    因此入库前把中文切成带空格的词序列。"""
    parts = []
    for tok in jieba.cut(text, HMM=False):
        parts.append(tok)
    return ' '.join(parts)
```

> 写入示例：正文 `容器内部无法访问宿主机` → 索引文本 `容器 内部 无法 访问 宿主机` → 搜索 `容器`、`无法` 均可命中。**搜索引擎只拿这段文本做 FTS，展示仍用原始 Markdown。**
>
> 依赖说明：jieba 为本地确定性词典库（约几 MB，纯 Python），随 scripts 一起入库，满足"零外部服务"约束。若坚持零第三方依赖，可退化为"逐字加空格"（召回高、精度低）或 `trigram` tokenizer（实测对 ≤2 字中文词匹配不稳，不推荐作为主方案）。

### 4.3 检索 SQL（v2 重写，已实测可运行）

```sql
-- 结构化过滤 + FTS5 全文检索（BM25 排序）
-- :query      经 jieba 分词后的查询词（空格分隔）
-- :tag       标签精确匹配（可为 NULL）
-- :severity  严重度（可为 NULL）
-- :project   项目（可为 NULL）
WITH hits AS (
    SELECT f_map.id AS exp_id, bm25(experiences_fts) AS relevance
    FROM experiences_fts
    JOIN fts_map f_map ON f_map.fts_rowid = experiences_fts.rowid
    WHERE experiences_fts MATCH :query          -- 注意：用表名限定，见下
),
scored AS (
    SELECT h.exp_id,
           e.file_path,
           e.occurrence,
           e.severity,
           e.project,
           -- FTS5 bm25 返回负值，越小越相关；把负相关度取负后与热度加权
           (-h.relevance) * 1.0
           + LOG(1 + e.occurrence) * 0.5         AS score
    FROM hits h
    JOIN experiences e ON e.id = h.exp_id
    WHERE (:tag IS NULL OR e.id IN (
              SELECT exp_id FROM experience_tags WHERE tag = :tag))
      AND (:severity IS NULL OR e.severity = :severity)
      AND (:project IS NULL OR e.project = :project)
)
SELECT exp_id, file_path, occurrence, severity
FROM scored
ORDER BY score DESC
LIMIT :limit;
```

> **v2 修正点（均有实测依据）**：
> 1. FTS5 的 `bm25()` 返回**负值**（实测高相关 ≈ -0.86，低相关 ≈ -0.76），v1 的 `1.0/(rank+1.0)` 会令排序反转，v2 取 `-relevance` 后再加权。
> 2. FTS 虚拟表**没有业务 `id` 列**（实测 `SELECT id FROM fts` 报 `no such column`），必须经 `fts_map` 桥接。
> 3. `MATCH :query` 中查询词同样需要经 `tokenizer.segment_for_fts()` 预处理；含 OR 逻辑的短语由上层组装。
> 4. 标签走关联表精确匹配，不再 `LIKE '%tag%'`。

## 五、指纹去重机制

### 5.1 指纹生成算法（v2 修正边界问题）

```python
import hashlib
import re

def extract_section(content: str, heading: str) -> str:
    """提取 '## <heading>' 到下一个 '## ' 之间的文本，找不到返回空串。"""
    m = re.search(rf'^##\s+{heading}\s*$(.*?)(?=^##\s|\Z)', content,
                  re.MULTILINE | re.DOTALL)
    return m.group(1).strip() if m else ''

def normalize(text: str) -> str:
    text = text.lower()
    # 1) 归一化变量：IPv4 / IPv6 / 端口 / 路径 / 十六进制长串 / 独立数字
    text = re.sub(r'\b\d{1,3}(\.\d{1,3}){3}\b', ' [ip] ', text)
    text = re.sub(r'(?::|：)\d+', ' [port] ', text)      # 端口（含全角冒号）
    text = re.sub(r'[A-Za-z]:[\\/][\w\-.\\/]+', ' [path] ', text)   # Windows 路径
    text = re.sub(r'[\\/][\w\-.\\/]+', ' [path] ', text)            # POSIX 路径
    # v2：\b\d+\b 对紧贴中文的数字无效（中文属 \w），改用前后非数字的宽断言
    text = re.sub(r'(?<!\d)\d+(?!\d)', ' [num] ', text)
    # 2) 压缩空白 + 规范化标点（全角→半角）
    text = text.replace('：', ':').replace('，', ',').replace('（', '(').replace('）', ')')
    text = re.sub(r'\s+', ' ', text).strip()
    return text

def generate_fingerprint(content: str) -> str:
    现象 = extract_section(content, '现象')
    证据 = extract_section(content, '关键证据')
    # 取现象全文（短而稳定）；证据只取前若干行（长日志差异不应导致漏判）
    证据核心 = '\n'.join(证据.splitlines()[:5])
    error_text = 现象 + '\n' + 证据核心
    normalized = normalize(error_text)
    return hashlib.sha256(normalized.encode('utf-8')).hexdigest()
```

> **v2 修正点**：
> 1. 数字归一化从 `\b\d+\b` 改为 `(?<!\d)\d+(?!\d)`——修复"错误码404"这类紧贴中文字符的数字无法归一化的问题。
> 2. 证据只取前 5 行参与指纹——修复 v1"取前 200 + 后 100 字符"导致的①头尾相似中间不同的两篇误判为重复、②长日志尾部变量干扰。
> 3. 现象全文入指纹（现象通常短且稳定）；不再按长度截断。

### 5.2 去重流程（v2 重构，修复生命周期缺陷）

> v1 缺陷回顾：合并时"不写入新文件"但磁盘上的新 md 已存在 → 每次增量扫描都会把它当新文件再次合并 → `occurrence` 无限 +1；且 occurrence/tags 只存 SQLite，索引重建即丢失。
> v2 规则：**真源（md 文件）负责累计，索引只做镜像**。

```python
def process_new_file(file_path, body):
    """新文件入库。返回 'inserted' | 'merged_into:<path>' | 'quarantined'"""
    meta = parse_frontmatter(body)          # 解析失败 -> 抛 FormatError

    # 查重：走唯一索引，O(log N)
    existing = db.query_one(
        "SELECT id, file_path FROM experiences WHERE fingerprint = ?",
        generate_fingerprint(body))

    if existing is None:
        _insert_new(file_path, meta, body)
        return {"action": "inserted"}
    else:
        _merge_into_existing(existing, file_path, meta, body)
        return {"action": "merged_into", "path": existing.file_path}

def _merge_into_existing(existing, dup_path, dup_meta, dup_body):
    """把重复文件合并进既有经验。唯一真源上的变更都在一个事务里。"""
    with db.transaction():
        # 1. 读被保留文件的当前 Frontmatter，累计并写回（真源！）
        kept_body = read_file(existing.file_path)
        kept_meta = parse_frontmatter(kept_body)
        kept_meta.occurrence += 1
        kept_meta.tags = merge_tags(kept_meta.tags, dup_meta.tags)
        kept_meta.related = merge_related(kept_meta.related, dup_meta.id,
                                          must_exist=[existing.id])  # 只收真实 id
        kept_meta.updated_at = now()
        write_file(existing.file_path, render_md(kept_meta, kept_body))

        # 2. 解决方案若更详细则追加（可选启发：保留较长者）
        #    （v2 建议至少保留一条说明，见 5.4 注意事项）

        # 3. 重复文件移入 duplicates/ 归档（不删除，可审计）
        move_file(dup_path, f"duplicates/{basename(dup_path)}")

        # 4. 更新索引（内容变了，指纹可能也变）
        update_existing_file(existing.file_path, sha256_file(read_file(existing.file_path)))

    # 5. git 提交由上层统一调度（见第 10 章），此处不提交

# 辅助函数：merge_tags 保留并集，merge_related 只保留真实存在的 id
def merge_tags(existing, incoming):
    merged = set(existing)
    for t in incoming:
        merged.add(t)
    return sorted(merged)

def merge_related(existing, incoming_id, must_exist):
    ids = set(existing) | {incoming_id}
    # 只保留真实存在的 id（此处简化，实际可从 DB 查）
    return sorted(ids & set(must_exist))
```

### 5.3 索引重建不丢累计状态

由于 `occurrence`、合并后的 `tags`、`related` 都写回了被保留 md 的 Frontmatter，`rebuild.py` 全量重建时只需**从 md 重新解析**即可还原全部累计状态。SQLite 中不再存在"只存在于库、md 中没有"的状态字段（`content_hash`、`fingerprint`、`file_mtime` 等纯缓存字段除外）。

### 5.4 去重注意事项（v2 补充）

- 合并时只 +1 出现次数会丢失重复文件里"更新、更完整的解决方案"。**建议策略**：若重复文件的 `## 解决方案` 章节文本与被保留者不同且更长，则以重复文件的方案为准做合并记录（追加为新小节 `## 解决方案（变体 N）` 或在 Frontmatter 加 `variants: [exp-...]` 关联）。至少不应静默丢弃。
- `related` 只允许指向**已真实存在的经验 id**，防止死链。

## 六、增量更新机制

### 6.1 变更检测（v2 修正：整表载入，避免每文件一次 SQLite 查询）

> v1 缺陷：逐文件 `db.query` 做点查，10,000 文件 = 10,000 次 Python↔SQLite 往返，与"50ms"性能声明矛盾。

```python
def incremental_index(root):
    # 1. 一次性载入 DB 现有记录（仅三列，内存极小）
    known = {row.file_path: row
             for row in db.query(
                 "SELECT file_path, content_hash, file_mtime FROM experiences")}

    # 2. 遍历磁盘文件，仅 stat（不读内容）
    for md_file in glob(f"{root}/knowledge/experiences/*.md"):
        stat = os.stat(md_file)
        rec = known.get(md_file)

        if rec is None:
            process_new_file(md_file)                 # 新文件
        elif rec.file_mtime != int(stat.st_mtime):
            new_hash = sha256_file(md_file)           # 仅此分支读内容
            if new_hash != rec.content_hash:
                update_existing_file(md_file, new_hash)
            else:
                touch_mtime_only(md_file, stat)       # touch，内容未变

    # 3. 清理：DB 中有记录但磁盘文件已不存在（被移入 duplicates 或手动删除）
    for path in set(known) - disk_files:
        remove_record_and_fts(path)
```

### 6.2 文件修改后的更新流程（v2 修复映射表垃圾累积）

```python
def update_existing_file(file_path, new_hash):
    meta, body = parse_md(file_path)

    with db.transaction():
        # 1. 更新主表
        db.execute("""
            UPDATE experiences
            SET tags = ?, severity = ?, category = ?, project = ?,
                status = ?, occurrence = ?, content_hash = ?, updated_at = ?
            WHERE file_path = ?
        """, (meta.tags, meta.severity, meta.category, meta.project,
              meta.status, meta.occurrence, new_hash, meta.updated_at, file_path))

        # 2. 重建 tags 关联（先删后插，杜绝残留）
        db.execute("DELETE FROM experience_tags WHERE exp_id = ?", (meta.id,))
        db.executemany("INSERT INTO experience_tags VALUES (?, ?)",
                       [(meta.id, t) for t in meta.tags])

        # 3. 【v2】FTS5：先删旧行（含 fts_map 里的映射，避免垃圾累积），再插入新行
        db.execute("""
            DELETE FROM experiences_fts
            WHERE rowid IN (SELECT fts_rowid FROM fts_map WHERE id = ?)
        """, (meta.id,))
        db.execute("DELETE FROM fts_map WHERE id = ?", (meta.id,))
        # 正文章节从 body 提取（meta 只是 Frontmatter）
        fts_content = segment_for_fts(' '.join(filter(None, [
            extract_section(body, '现象'), extract_section(body, '根因'),
            extract_section(body, '解决方案'),
            extract_section(body, '关键证据')])))
        cur = db.execute("INSERT INTO experiences_fts (content) VALUES (?)",
                         (fts_content,))
        db.execute("INSERT INTO fts_map (id, fts_rowid) VALUES (?, ?)",
                   (meta.id, cur.lastrowid))

        # 4. 指纹变化（核心内容变了）→ 唯一索引冲突需特殊处理
        new_fp = generate_fingerprint(body)
        old_fp = db.query_one("SELECT fingerprint FROM experiences WHERE id = ?",
                              meta.id).fingerprint
        if new_fp != old_fp:
            clash = db.query_one(
                "SELECT id FROM experiences WHERE fingerprint = ? AND id <> ?",
                new_fp, meta.id)
            if clash is not None:
                # 改完内容后与另一条经验撞指纹：视为重复，走 5.2 合并
                _merge_into_existing(clash, file_path, meta, body)
                return
            db.execute("UPDATE experiences SET fingerprint = ? WHERE id = ?",
                       (new_fp, meta.id))
```

### 6.3 格式校验与坏文件隔离（v2 新增）

`parse_frontmatter()` 失败（缺必填字段 / YAML 语法错误 / id 格式非法）时：

1. 把文件移动到 `quarantine/`（不改名，保留原名便于排查）；
2. 在 `index/rebuild.log` 记录 `[quarantine] <file>: <原因>`；
3. 不影响其他文件继续索引。

> 这是 mem-gen 生成质量不可控时的兜底，避免"一条坏文件搞崩全量重建"。

## 七、性能基准（v2 按真实实现重估）

> v1 基准与实际实现不符（见 6.1）。v2 下表基于修正后的实现估算，并为"基准环境"留出说明位。

| 操作 | 文件数 | 估算耗时 | 实现要点 |
| :--- | :--- | :--- | :--- |
| 新增 1 个经验 | - | < 30ms | 读文件 + 解析 + jieba 分词 + 指纹 + 事务写 |
| 合并 1 个重复经验 | - | < 30ms | 读两个文件 + 写回 Frontmatter + 移动文件 + 更新索引 |
| 增量检测（无变化） | 1,000 | ~10ms | 整表载入（一次 SQLite 查询）+ 1,000 次 stat |
| 增量检测（无变化） | 10,000 | ~100ms | 同上，瓶颈是 10,000 次文件系统 stat |
| 全量重建 | 1,000 | ~5s | 读全部文件 + jieba 分词 + 重建索引 |
| 全量重建 | 10,000 | ~60s | 一次性操作，仅新环境执行 |

> 说明：jieba 首次加载词典约 0.3–1s（一次性）；`LOG`、BM25 运算可忽略。标称值为单机 SSD + Python 3.11 的典型区间，精确数字以落地后 `indexer.py --bench` 实测为准。**v2 不再承诺 v1 那种脱离实现的"50ms / 1 万文件"数字。**

### 7.1 性能优化要点

| 优化策略 | 实现方式 | 效果 |
| :--- | :--- | :--- |
| 事务批量 | 每批文件包 `BEGIN`/`COMMIT`，进程启动 `PRAGMA journal_mode=WAL` | 写入与查询并发不互锁 |
| 增量检测不读内容 | 整表载入内存 + `os.stat()` 对比 | 无变化时零文件读 |
| 指纹唯一索引 | `fingerprint` UNIQUE | 查重 O(log N) |
| 中文分词缓存 | 同文件 hash 未变跳过分词（复用 content_hash 判断） | 修改 tags 时不必重分词 |

## 八、Agent 集成（DSH 真实扩展机制，双源取证定稿）

> **v2 重写说明**：v1 假设的 `hooks.on('session:start')` / `ctx.systemPrompt += ...` **在 DSH 中不存在**。真实扩展面是 Cordis 插件框架（`@deepseek-ai/cordis`）上的三组服务：`ctx.tools`（工具）、`ctx.systemPrompt` / `ctx.on`（上下文与事件）、`ctx.settings`（配置）。本章结论**双重取证**：① 本机已装插件源码（`dsh-codegraph`、`@nsfocus/nf-bug-progress`、`dsh-tool-fs`）；② 对 DSH 全量源码的独立调研（文件行号均已标注）。分四个落地层次，从**零代码**到**全动态**。

### 8.0 首选方案（零代码）：`~/.dsh/AGENTS.md` 自动注入

DSH 的 `dsh-agent-instructions` 插件会自动发现并注入 **`$DSH_HOME/AGENTS.md`**（`~/.dsh/AGENTS.md`，用户全局）+ 项目根→cwd 祖先链上的 `AGENTS.md`/`CLAUDE.md`/`*.local.md`，渲染成 `<system-reminder>` 包裹的消息注入会话，并经 `agent/pre-step` 在每步生效（证据：`dsh-agent-instructions/lib/index.js:15-17, 110-115, 554, 571, 1100-1196, 1271-1288`）。

**PERSONA 摘要 + 检索规则只要写一个文件即可全局常驻，零插件代码**：

```markdown
<!-- %USERPROFILE%\.dsh\AGENTS.md -->
# 记忆库使用规则（dsh-memory）

- 知识库根：`~/.dsh-memory`（Git 仓库，md 为唯一真源，SQLite 索引可重建）
- 当用户描述错误、报障或提问时，先检索历史经验再作答：
  用 MCP 工具 `mcp__memory__memory_search` 查询，命中则参考其"根因/解决方案"；
  需要细节时调 `mcp__memory__memory_read`。
- 完成一次有复用价值的排障/踩坑后，调用 `mcp__memory__memory_save`
  沉淀经验（模板含 Frontmatter，见 `~/.dsh-memory/knowledge/experiences/` 示例）。
- 本文件由记忆系统 v2 方案维护，避免与其它 AGENTS.md 指令冲突。
```

> **工具名前缀说明**：上述模板假设走 8.1b MCP 方案（`serverName: memory` → 工具名 `mcp__memory__memory_search`）。若采用 8.1 方案 A（原生 `ctx.tools.register`），工具名无前缀，模板中 `mcp__memory__memory_search` 改为 `memory_search` 即可。选择哪种就在 AGENTS.md 里写哪种，保持一致。
```

**启用前提**：Web profile 已挂 `agent-instructions` 行（`dsh-base` 默认带，`standard` preset 亦有真例）。若想分 Agent 定制（如只在某 preset 生效），改用该 preset 的 `agent.cordis.yml` 挂 `- id: agent-instructions` 行（证据：`dsh-agent-presets/lib/index.js:131-145, 707-735`）。

> 代价与边界：AGENTS.md 是**静态指令**，不能"启动时算 top-3 再注入"；若需要动态内容（按 occurrence 现算），走 8.3 的动态注入。多数场景静态规则已够用，故列为首选。

### 8.1 工具通道（方案 A，内嵌原生工具）：自写插件 + `ctx.tools.register()`

DSH **原生支持**注册工具，内置 `read`/`write` 等即用此入口（证据：`dsh-tool-fs/lib/index.js:332-400`；注册器 `dsh-tools/lib/index.js:2524, 2762-2770`）。这是比"外部 MCP 服务器"更轻量的形态——工具直接跑在 DSH 进程内，调用本机 Python 索引脚本即可：

```typescript
// plugins/dsh-memory/lib/index.js（宿主半体）
import { definePlugin } from '@hyzyn/dsh-kit'   // 或 @deepseek-ai/cordis
import { execFile } from 'node:child_process'
import { promisify } from 'node:util'
const exec = promisify(execFile)

const plugin = definePlugin({
  name: 'dsh-memory',
  inject: [],
  apply(ctx, config) {
    const memoryDir = config?.memoryDir || join(homedir(), '.dsh-memory')

    // 工具 1：memory_search —— 内部调用 4.3 节 SQL（python 子进程跑 scripts/query.py）
    ctx.tools.register({
      name: 'memory_search',
      description: '按关键词/标签/严重度检索历史经验库，返回命中的经验路径与摘要。',
      parameters: {
        query:    { type: 'string',  description: '错误描述或关键词（中文可，内部做 jieba 分词）' },
        tag:      { type: 'string',  description: '按标签过滤（可选）' },
        severity: { type: 'string',  enum: ['high','medium','low'], description: '按严重度过滤（可选）' },
        limit:    { type: 'integer', description: '返回条数，默认 5' },
      },
      async execute(args) {
        const { stdout } = await exec('python', [
          join(memoryDir, 'scripts/query.py'), JSON.stringify(args),
        ], { cwd: memoryDir })
        return stdout
      },
    })
    ctx.tools.register({
      name: 'memory_save',
      description: '保存一条经验（含 Frontmatter 的完整 Markdown）到知识库，供索引器消费。',
      parameters: { content: { type: 'string', description: '完整 Markdown（含 ---frontmatter---）' } },
      async execute(args) {
        const { stdout } = await exec('python',
          [join(memoryDir, 'scripts/save.py'), JSON.stringify({ content: args.content })],
          { cwd: memoryDir })
        return stdout
      },
    })
    ctx.tools.register({
      name: 'memory_read',
      description: '读取某条经验的完整 Markdown 原文。',
      parameters: { id: { type: 'string', description: '经验 ID，如 exp-20260901-001' } },
      async execute(args) {
        const { stdout } = await exec('python',
          [join(memoryDir, 'scripts/read.py'), JSON.stringify(args)],
          { cwd: memoryDir })
        return stdout
      },
    })
  },
})
export const { name, inject, apply } = plugin
```

> `defineTool()`/`ctx.tools.register()` 的 `parameters` 会被编译为 JSON Schema 自动暴露给模型（证据：`dsh-tools/lib/index.js:800-808, 836-882`）。注册为全局或 per-agent 皆可（L2762-2770）。**该方案工具名干净（`memory_search`，无前缀）、无额外进程**，推荐为主方案。

### 8.1b 工具通道（方案 B，进程外）：MCP 服务器（备选，可复用任意语言）

若想让记忆服务**与 DSH 进程解耦**（语言无关、可独立测试），做 stdio MCP 服务器，再注册一行 MCP 客户端。工具名自动为 **`mcp__<serverName>__<tool>`**（证据：`dsh-mcp-client/lib/index.js:119-125, 150-173`）。

先在 `$DSH_HOME/profiles/web/cordis.patch.yml` 加行（需先 `dsh plugin --profile web add @deepseek-ai/dsh-mcp-client`）：

```yaml
- id: mcp-memory
  name: '@deepseek-ai/dsh-mcp-client'
  config:
    transport: stdio            # 或 streamable-http + url/headers
    serverName: memory          # → 工具名 mcp__memory__memory_search 等
    command: python
    args: [ "%USERPROFILE%\\.dsh-memory\\scripts\\mcp_memory.py" ]
    cwd: "%USERPROFILE%\\.dsh-memory"
```

> **取舍**：方案 A 简单直接、工具无前缀；方案 B 隔离进程、多语言、便于其它 Agent（非 DSH）复用同一记忆服务。本方案倾向 A，但存储/索引层设计成两方案共用（scripts/ 独立可调用），切换成本低。

### 8.2 上下文通道：PERSONA 与检索规则注入（静态优先）

按注入层级由简到繁：

1. **零代码**：写 `~/.dsh/AGENTS.md`（见 8.0）——静态 PERSONA + 检索规则，推荐首选。
2. **systemPrompt 分区**：DSH 的 system prompt 是分区组装（`dsh-system-prompt/lib/index.js:152-230`），官方预留 **`deployment:persona` 槽位（order 0）**，每会话自动携带（`dsh-base/cordis.patch.yml:429-432`）。自写插件通过 `ctx.inject(['systemPrompt'])` + `promptCtx.systemPrompt.section({name, order, text})` 追加自定义区块（对照 `@hyzyn/dsh-codegraph` 源码 724–736 行的 announcement 注入，即本会话系统提示中 `<!-- CODEGRAPH_START -->` 段的来源）。
3. **动态注入**：需要"启动时按现状计算"的内容，用 `ctx.on('agent/session-start', ({ agent }) => agent.inject(userMessage))` 在会话开始播种（证据：`dsh-agent/lib/types/runtime-types.d.ts:211-223` session-start 挂点、`:130-133` `agent.inject(message: UserMessage)` 签名）。8.3 说明为何不建议用它塞"高频 top3"。

```typescript
// 方式 2 的插件骨架（自写插件内）
ctx.inject(['systemPrompt'], (promptCtx) => {
  promptCtx.effect(() => {
    const persona = readFileSync(join(memoryDir, 'PERSONA.md'), 'utf8').slice(0, 500)
    return promptCtx.systemPrompt.section({
      name: 'plugin:dsh-memory:persona',
      order: 200,                       // order 越小越靠前；deployment:persona 占 0
      text: `## 关于我（来自记忆库 PERSONA.md）\n${persona}`,
    })
  }, 'dsh-memory: persona')
})
```

> 8.0 的 AGENTS.md 与 8.2 的 section 二选一即可（推荐 AGENTS.md）；同时使用会造成重复注入。**persona 内容本身存哪**：`PERSONA.md` 存记忆库（随 git 迁移），AGENTS.md 只写"去 `~/.dsh-memory` 读 PERSONA.md"的指引，避免双份维护。

### 8.3 为什么不注入"高频经验 top3"

v1 计划把按 occurrence 排序的前 3 条经验全文塞进每次会话。**v2 不建议**：

1. **污染固定上下文**——与当前问题无关的高频经验是噪音，且挤占 token；
2. **静态注入做不到"取当前最热"**——`agent/session-start` 动态注入虽可行，但每次会话都要跑一次查询并把全文塞进首轮消息，收益远小于成本；
3. **检索应发生在对话流中**——问题出现时按需 `memory_search`，比预注入精准得多。

替代：`memory_search` 在 `query` 为空时默认按 `score = LOG(1 + occurrence) DESC` 返回最近高频经验（把"回顾常用坑"变成一次显式调用）。

### 8.4 兜底：无任何插件也能用

记忆库本质是**普通文件 + 普通 Python 脚本**：模型拿到 AGENTS.md 指引前，也可直接 `read` 工具读 `~/.dsh-memory/knowledge/experiences/*.md`，`pwsh` 跑 `python scripts/indexer.py`。即 1–7、9–15 章存储与索引部分**不依赖 DSH 扩展通道即可先落地**；第 8 章只是"最后一公里"的接线，按 8.0 → 8.1 → 8.2 顺序逐步接通即可。

> **调研结论备忘**：DSH 无内置记忆引擎（全库检索 `memory`/`experience` 无相关实现），`mem-gen` 亦非内置——本方案即填补此空白；MCP 工具命名固定为 `mcp__<serverName>__<tool>`；系统提示为分区组装、支持 order 排序；会话生命周期事件 `session/created`、`agent/session-start`、`agent/pre-step` 等均为 Cordis `ctx.on`/waterfall 形态。

### 9.3 为什么索引要重建而不是复制 .db？（保留，补充一句）

| 问题 | 说明 |
| :-- | :-- |
| **系统架构差异** | SQLite 文件在 x86 和 ARM 间可能不兼容 |
| **SQLite 版本差异** | 不同版本 FTS5 存储格式可能有变化 |
| **确定性保证** | 重建确保索引完全基于当前 MD 文件，无脏数据 |
| **文件路径变化** | 新环境的工作目录可能不同 |

> v2 补充：因为累计状态（occurrence/tags/related）已写回 md Frontmatter（真源），重建不丢任何业务数据；索引本就是缓存，丢了重建即可。**Windows 下建议同时提交 `.gitattributes`（`*.md text eol=lf`）**，避免换行符差异造成 Git 噪音与 content_hash 抖动。

## 十五、总结（v2 更新）

这套方案的核心价值：

1. **零外部服务依赖** — 不需要 embedding 服务、不需要向量数据库、不需要网络；jieba 是本地确定性词典
2. **纯文本资产** — 所有知识是你能读懂、能编辑、能 Git 管理的 Markdown；**累计统计也写回 md，索引只是缓存**
3. **可迁移永生** — 整个目录带走，任何地方 `git clone` + `rebuild` 即可复活
4. **真实可运行** — v2 修正了 v1 检索 SQL 的三处实测硬伤与去重生命周期缺陷，SQL 均已在本机 SQLite 3.50 验证
5. **中文可用** — 预分词方案使中文按词检索成立（v1 声明不实，v2 用 jieba 补上）
6. **与现有工作流兼容** — `mem-gen` 生成的 md 直接纳入，模板只新增两个时间字段
