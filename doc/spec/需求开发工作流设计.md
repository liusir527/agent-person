# 需求开发工作流设计（由 bug-fix-workflow 推导）

> 目的：把当前 `bug-fix-workflow`（BUG 修复）的成熟骨架——状态机引擎 + 门禁硬校验 +
> 对抗评审 + worktree 隔离 + 进度可观测 + 闭环沉淀——平移、适配到**需求开发**场景。
> 本文件是设计稿，给出可落地为独立 skill（如 `requirement-dev-workflow`）的完整 flow。
>
> 设计基线：`.dsh/skills/bug-fix-workflow/`（SKILL.md / state_machine.py / references/ / templates/）
> 与 `<workspace_root>/hooks/AGENT.md`「BUG 修复流程铁律」。

## 1. 为什么需求开发需要独立 flow（而非套用 bug-fix-flow）

| 维度 | BUG 修复 | 需求开发 |
|------|---------|---------|
| 驱动输入 | BUG 单/问题描述（现象已知） | 需求单/PRD/口头需求（目标已知，路径未知） |
| 首阶段动作 | 找**根因**（追溯产生方/消费方） | 澄清**目标**（理解→范围→拆解→验收标准） |
| 核心产物 | 问题分析结论（证明"为什么坏"） | 需求设计说明书（证明"怎么建"） |
| 审查口径 | 分析结论**可复现** | 设计方案**可推演/可测试**（对照验收标准） |
| 用户确认点 | 1 个（修改方案） | ≥2 个（需求理解+验收标准、实施计划） |
| 验证终点 | 上机基础测试 + 人工验证 | 单测/集成/上机测试 + 人工验收（按验收标准） |
| 收尾 | 关闭工单 + 沉淀 | 合并/部署上线 + 沉淀（可能含文档/demo） |
| 规模/风险 | 小、局部 | 大、可能跨 WEB/AGENT/VPP 三层 → 更吃影响评估与回归 |
| 技术栈/领域 | 修复遍布各层 | 聚焦 **VPP（npp，C 语言）后端**；配置管理在 AGENT/WEB；测试常在**受限环境**（无完整联调） |

共同可复用的骨架（直接平移，不改）：
- 状态机引擎：先 init 再动作 / micro/advance / gate-check / confirm / resolve / progress；
- 门禁三型：对抗评审自动置位、人工 confirm、证据型（--evidence）；
- worktree 隔离 + codegraph 索引 + dirs.json 放行；
- 进度可观测（progress.md + 阶段横幅）；
- 闭环强制沉淀（memory-gen + memory-push）；
- 外部状态变更确认规范（合并/部署/上线 归"谁操作"询问）；
- 分层任务边界（WEB/AGENT/VPP 取证的防扩散约束）。

## 2. 主状态机（8 态）

```
需求澄清 → 需求分析 → 方案评审 → 出实施计划 → 编码实现 → 测试验证 → 交付上线 → 结束
```

与 bug-fix 的对应关系（7 态 → 8 态，多出的首态承担"理解+拆解"）：

| bug-fix 主状态 | 需求开发主状态 | 差异说明 |
|---|---|---|
| 分析（取证→假设→验证→结论） | **需求澄清** | 不找根因，改做"理解目标"；需求常需反向提问回补 |
| （同上，后半） | **需求分析** | 现状调研 + 数据流梳理 + 方案设计 + 影响评估（设计是产出而非追溯） |
| 审查结论（审查→复现→判定） | **方案评审** | "复现"改为"按验收标准可推演/可测试" |
| 出修改方案（…→用户确认） | **出实施计划** | 方案变计划，任务拆解更细 |
| 编码（修改→代码审查→编译通过） | **编码实现** | 同名骨架 |
| 上机验证（自测→基础测试→人工验证） | **测试验证** | 按验收标准执行单测/集成/上机 + 人工验收 |
| 更新BUG单（…→关闭工单→沉淀） | **交付上线** | 关闭工单 → 合并/部署上线 + 沉淀 |
| 结束 | **结束** | 相同 |

## 3. 微观状态与退出产物

| 主状态 | 微观状态（有序） | 退出产物（advance/close 门禁按文件名查磁盘） |
|--------|-----------------|--------------------------------------------|
| 需求澄清 | 需求理解 → 范围界定 → 需求拆解 → 验收标准 | `需求理解说明书.md` |
| 需求分析 | 现状调研 → 数据流梳理 → 方案设计 → 影响评估 | `需求设计说明书.md` |
| 方案评审 | 评审 → 可验证性推演 → 判定 → 轮次记账 | `评审结果-rN.md` |
| 出实施计划 | 计划草拟 → 任务拆解 → 用户确认 | `实施计划.md` |
| 编码实现 | 修改 → 代码审查 → 编译通过 → 修复评审问题 | （编译产物，deploy-build 验证） |
| 测试验证 | 自测记录 → 受限环境测试执行 → 转人工验收 → 人工验收通过 | `测试记录.md`（含交接项登记，见 §6.4） |
| 交付上线 | 生成MR描述 → 提交MR → 人工review → 合并部署 → 沉淀经验 | `MR描述.md` + `交付说明.md` |
| 结束 | （无） | — |

## 4. 门禁设计（gates）

| 门禁 | 置位方式 | 说明 |
|------|---------|------|
| `requirement_confirmed` | 人工 `confirm`（需求方/用户） | 需求理解 + 验收标准已对齐；禁止 `gate` 手拍 |
| `design_reviewed` | 方案评审 PASS 自动置位 | 只有对抗评审（≤3 轮，FAIL<3 回「需求分析」，第 3 轮 FAIL 转人工）可置位 |
| `plan_confirmed` | 人工 `confirm` | 实施计划已确认 |
| `worktree_ready` | `worktree-set` 自动置位 | 编译机 `feature-<需求号>` worktree 已派生登记 |
| `code_reviewed` | 证据型 `--evidence`（`代码审查报告-rN.md`） | 代码改动经 code-reviewer 审查 PASS；无证据文件拒绝置位 |
| `build_passed` | 证据型 `--evidence` | 编译日志 |
| `test_handed` | 脚本/自动 | 已转人工验收 |
| `test_passed` | 人工 `confirm` | 人工验收通过（按验收标准逐条） |
| `mr_reviewed` | 人工 `confirm` | MR 经人工 review |
| `merged`/`delivered` | 人工 `confirm` | 合并/部署上线完成（记事实，不代操作，见 §8） |
| 沉淀经验 | close 前校验微观状态 | 须推进到「沉淀经验」才可 close |

advance 门禁（节选，对应 bug-fix `gate_prereq` 模式）：
- 需求澄清→需求分析：`需求理解说明书.md` 存在非空；
- 需求分析→方案评审：`需求设计说明书.md` 存在非空；
- 方案评审→出实施计划：`gates.design_reviewed=true`；
- 出实施计划→编码实现：`实施计划.md` 存在 + `plan_confirmed=true` + `worktree_ready=true`；
- 编码实现→测试验证：`code_reviewed=true` + `build_passed=true`；
- 测试验证→交付上线：`测试记录.md` 存在 + `test_passed=true`；
- 交付上线→结束（close）：`mr_reviewed=true` + `merged=true` + 微观状态=`沉淀经验` + `交付说明.md` 存在。

## 5. 铁律（写入 `<workspace_root>/hooks/AGENT.md`，镜像 bug-fix）

1. **先 init 再动作**：拿到需求单先 `requirement_state_machine.py init --req-id <单号> --title --module`，状态一律脚本驱动，禁止手改 state.json。
2. **验收标准先行**：无验收标准的方案不得进入编码（对应 BUG 的"根因未知不编码"）。
3. **评审通过才能编码**：设计方案未经对抗评审（按验收标准可推演/可测试）不得进入实施计划。
4. **用户确认双闸**：需求理解+验收标准、实施计划两处均须人工 `confirm`，禁止 `gate` 手拍。
5. **编码前门禁检查**：每次编码前 `gate-check`，拒绝（exit 2）则先补前置。
6. **推进必 advance / 编译必验证**：build_passed 须带编译日志证据。
7. **闭环必沉淀**：close 前 memory-gen（`.dsh-memory/knowledge/experiences/sparse/` + 索引）→ memory-push → `micro --to 沉淀经验` → 输出交付说明 → close。
8. **进度可观测**：自动刷新 `runtime/req/<单号>/progress.md`，回复带阶段横幅。
9. **外部状态变更规范**：合并/部署/上线 一律先问"谁操作"，代为执行绝不默认 Recommended。
10. **TDD 铁律**（吸收 superpower-TDD）：编码实现阶段，无失败测试不写生产代码；每个新增函数/行为先写失败测试（红）→ 最小实现（绿）→ 重构，验收标准必须先转成测试用例才有判据。
11. **完成前校验**（吸收 superpower-verification-before-completion）：任何"完成/通过"断言必须带当轮运行证据（命令输出/退出码/测试结果），禁止"应该/大概/似乎"或先满意后校验；证据型门禁（build_passed 等）即此原则的实例化。
12. **受限环境测试**（VPP 层领域约束）：测试常无完整联调环境；**能测的必须测**（单测/受限环境运行态/冒烟），**不能测的显式列「交接项」**（责任人+环境+时机）进 `测试记录.md`；禁止用"环境受限"当不测试的借口；`test_passed` 含"可测项全过 + 交接项已登记"（见 §6.4）。

## 6. 需求开发特有方法论（对应 BUG 分析五步法的适配）

### 6.1 需求澄清清单（需求理解说明书 必填）

- 需求原始描述（原样引用，勿改写）；影响版本/设备型号/分支；
- 归属层判断：WEB / AGENT / VPP（npp）——**配置管理类需求归 AGENT/WEB；VPP 需求聚焦转发/选路/运行态逻辑 + 经 biapi 暴露或接收的字段**；确需跨层先定"本次动哪层"，跨层另走分层 plan（见 §8）；
- 范围界定：in-scope / out-of-scope 显式列出；
- 需求拆解：拆成可独立交付的子任务（story）；
- **验收标准**：每条可量化/可判定（命令输出、字段值、行为），这是后续评审与测试的唯一标尺；
- 待确认项：信息不足时聚焦反向提问，不泛问。

### 6.2 需求设计五步法（需求设计说明书 必填，审查 FAIL 项同 bug-fix）

1. **先画数据流再设计**：新字段/新流程同样要写 `谁产生 → 谁消费 → 怎么消费 → 空/边界怎么办`；
2. **参考方案只作线索不作答案**：借鉴旧需求/同模块实现必须验证在当前分支成立；
3. **强制自我证伪**：列出"这个设计在哪些场景不成立"；列不出 = 没想透，不进实施计划；
4. **必须追到边界态**：至少四类——输入为空/超限、状态全失效、来源异常、并发竞争；每个边界态转测试用例；
5. **推进前提**：全门禁一关不能跳。

> 记忆口诀（改自 BUG 版）：**验收 ≠ 现象，参考 ≠ 答案，证伪才敢定设计，边界才叫完整，门禁一关不能跳。**

### 6.3 代码审查闭环（编码实现 主状态的强制环节，直接复用 bug-fix 实现）

> 原工作流中 codereview 不是"一个微观状态名字"，而是完整闭环：code-reviewer agent +
> 证据型门禁 + 多轮复审循环。需求开发 flow 完整平移，且 **`code-reviewer` agent 审查的是
> 代码改动本身（场景无关），直接复用现有 `.dsh/agents/code-reviewer/code-reviewer.md`，无需新建**。

**闭环路径（编码实现 主状态内）：**

```
编码实现：修改 → 代码审查 → 编译通过 → 修复评审问题
                │
                ├─ FAIL(轮次<3) ──→ 回「修改」重新修复 ──→ 复审
                └─ 第 3 轮 FAIL ──→ 转人工接管（human_takeover=true，停止自动推进）

代码审查 PASS ──→ gate --flag code_reviewed --value true \
                      --evidence <代码审查报告-rN.md>  （证据型门禁：无文件 exit 2 拒绝）
        │
        └─ build_passed 也置位后 ──→ advance --to 测试验证
```

**审查对象与维度**（code-reviewer 逐文件审查 `git diff`，五维缺一判 FAIL）：
1. **正确性**：改动是否实现实施计划声明的逻辑？分支/边界态/空指针/资源释放是否处理；
2. **最小性**：只动必要行，无与本需求无关的重构/风格重排/注释大改；
3. **风格一致**：缩进、命名、错误处理与所在文件一致；
4. **影响面**：调用方/依赖方/配置/测试/版本兼容/回滚成本；不触 task-boundary 层边界；
5. **编译可达**：新头文件依赖/新宏/新 struct 字段是否缺配套 .h。

**严重度分级**（P0/P1 阻塞 PASS，P2 仅记录）：
- P0：阻塞编译 / 引入回归 / 越权改层（跨层扩散）——必须修复；
- P1：会引发后续 bug / 与风格严重不一致——必须修复；
- P2：纯风格建议——不阻断 PASS。

**产物与轮次**：
- 落盘 `runtime/req/<需求号>/代码审查报告-rN.md`，结论行写 `审查通过：PASS` / `审查不通过：FAIL`；
- 最多 3 轮：FAIL 且轮次<3 → 主 agent 回「修改」修正后复审（向同一 reviewer 会话续问）；
- 第 3 轮 FAIL → 状态机置 `human_takeover=true`，转人工接管；
- PASS 后主 agent 调 `gate --flag code_reviewed --evidence <报告路径>` 置位（脚本校验报告文件存在非空）。

**评审时机与反馈处理（吸收 requesting/receiving-code-review）**：
- 评审时机：每任务完成后、重大功能完成后、合并到基线分支前各审一次（尽早评审、频繁评审）；
- 反馈分级：P0/Critical 立即修；P1/Important 进入下一步前必须修完；P2/Minor 记录择机处理；
- 接收反馈：先验证再实施，禁止"完全正确"式表演认同；外部评审意见须对照代码核实（是否破坏现有功能 / 是否 YAGNI / 评审者是否掌握完整上下文），有异议用技术理由反驳而非盲从。

**与 file-review skill 的协同**（两级审查，不冲突）：
- `file-review`：所有 write/edit 落盘文件的通用落盘审查（路径硬编码、编码、字段匹配、frontmatter…），触发即串接，≤3 轮降级人工；
- `code-reviewer`：编码主状态的正式门禁，审查**代码改动语义**（可合并性），是 `code_reviewed` 门禁的唯一证据来源；
- 顺序：编码落盘后先 file-review 过一遍通用问题，再派 code-reviewer 做语义审查，避免把 P2 类问题带进正式门禁。

### 6.4 受限环境测试策略（VPP 层常态约束）

> 领域背景：本工作流聚焦 **VPP（npp，C 语言）后端**，配置管理在 AGENT/WEB 层。实际需求测试时常无
> 完整三方联调环境，只能在**受限环境**验证。核心原则：**能测的必须测，不能测的显式列为交接项，
> 禁止用"环境受限"当不测试的借口。**

**环境分层与测试边界：**

| 层 | 可测项 | 不可测/受限项 |
|---|---|---|
| 编译层（编译机） | 编译通过、语法/ABI 可达、`*.api` 生成 api.json | — |
| VPP 运行态（受限设备/单机） | npp 服务启动、`vppctl`/CLI/show 命令、运行态字段、转发/选路行为（构造报文/CLI 操作）、模块逻辑 | 经 WEB/AGENT 的配置下发全链路 |
| 完整环境（WEB+AGENT+VPP） | 配置下发→VPP 生效→界面显示 端到端 | 通常不可用 |

**测试执行策略（按优先级）：**
1. **单测/逻辑验证**（本地可跑）：新增函数/模块用 C 单测（项目实际测试框架）验证逻辑与边界态（§6.2 四类边界态转用例）；无框架时用最小复现脚本，能本地闭环的先闭环；
2. **受限环境运行态验证**：VPP 单机启动 + 模块 show 命令核对运行态字段；构造报文/CLI 触发转发/选路路径核对行为；
3. **冒烟退化**：涉及 `*.api` 改动 → 上机验证退化为冒烟（npp 启动 + 基础命令）；biapi 变更后 vpp-agent 未同步时无法经 WEB/AGENT 下发，全量验证属交接项（同 bug-fix task-boundary §2）；
4. **人机协作**：配置类验证由 agent 出 `测试方案.md`，用户在（受限或完整）环境按方案配置，agent 检查并记录；
5. **交接项显式化**：凡因环境受限无法验证的用例，必须在 `测试记录.md` 中列为「交接项」（谁 / 在哪个环境 / 何时验证），由用户在完整环境补验后 `confirm test_passed` 或单独确认交接完成。

**验收判定规则（test_passed 置位条件）：**
- 受限环境下**能测的用例**：必须全部跑过——这是 `test_passed` 的硬性组成部分；
- **不能测的用例**：必须显式列「交接项」+ 明确责任人，禁止悄悄降级为"没测"；
- `test_passed` = 受限环境可测项全过 + 交接项已登记（完整环境验证可延后到交付后由用户/测试完成，属交付上线后的回归项）。

## 7. Superpowers 精华吸收（方法论强化）

> 将 superpowers 套件（本会话可用的 superpower-* 技能）中可复用的方法论并入需求开发 flow。
> 下表是「精华 → 落点」对照，§7.2 是其中对既有机制的具体强化点。

### 7.1 吸收对照表

### 7.2 对既有机制的强化点

1. **需求分类定级（吸收 brainstorming）**：需求澄清首步先分类——spike（可行性）/ bounded（本仓库小改动）/ architectural（跨层或新子系统）。architectural 走全门禁+完整设计文档；bounded 可简化产物但**审批关卡不放宽**；棘轮单向生效——中途发现隐藏复杂度只升级路径，不允许降级。
2. **TDD 与验收标准互为表里（吸收 TDD）**：验收标准（§6.1）先转成测试用例，编码实现阶段才做得到"先写失败测试"；两条铁律（2、10）构成需求开发的质量底座。
3. **任务级评审 + 台账（吸收 SDD）**：编码实现按实施计划拆任务，每个任务完成后做任务评审（规格符合度+代码质量），全部完成后做全分支评审；评审轮次对齐 code-review ≤3 轮。`runtime/req/<单号>/ledger.md` 台账记录进度与裁决（Ruling），防上下文压缩丢进度——与既有 progress.md 互补（progress 给用户看，ledger 给 agent 自己断点恢复用）。
4. **完成前校验实例化（吸收 verification-before-completion）**：证据型门禁（build_passed/code_reviewed）就是"断言必须带证据"的落点；除此之外，进入每个下一主状态前，上一状态的完成声明须能贴出当轮输出。
5. **交付三选项（吸收 finishing-branch）**：测试全过后呈现三选项（1. 本地合并回基线 2. 推送并建 MR 3. 保持分支现状）由用户决定；合并前确认基线分支（合错基线回滚成本高）；worktree 清理规则复用 §8 约定。
6. **失败 3 次质疑架构（吸收 systematic-debugging）**：编码/验证阶段同一问题修复失败 ≥3 次 → 停下质疑架构/方案并与用户讨论，不继续第 4 次盲修——与既有"3 轮 FAIL 转人工接管"的门禁思想同构。

## 8. 关键差异点的处理约定

| 差异点 | 约定 |
|--------|------|
| 需求跨层（WEB+AGENT+VPP） | 一次只动一层；确需跨层，分层 plan 并逐层门禁推进，先停手问用户 |
| 需求开发常有新表/新接口 | 涉及 `*.api` 改动编译后走 `vpp-api-sync` 暂存 api.json，上机验证退化为冒烟验证（同 bug-fix） |
| 配置类/业务类验证 | 人机协作：agent 先出 `测试方案.md`，用户配置，agent 检查记入 `测试记录.md` |
| 受限环境测试 | VPP 层测试常无完整联调环境；能测的必须测（单测/运行态/冒烟），不能测的列交接项；策略与验收判定见 §6.4 |
| 部署/上线 | 属外部状态变更：先问"谁操作"（您自行 / AI 代为 / 转他人），代执行绝不默认 Recommended，执行前回显精确动作 |
| 提交格式 | `feat: NEWNF-XXXXX 【模块】描述`（对应 bug-fix 的 `fix:`）；分支 `feature-<需求号>` |
| 状态目录 | `runtime/req/<需求号>/`（平行于 `bug-fix-state/`，门禁登记 dirs.json 逻辑复用） |
| 交付集成方式 | 测试全过后呈现三选项（本地合并/推送建 MR/保持分支现状）由用户决定；合并前确认基线分支；清理 worktree 规则复用（吸收 finishing-branch，见 §7.2-5） |

## 10. 落地步骤（建议顺序）

1. 按 §9 建 skill 目录与 10 份模板；
2. 复制 `state_machine.py` 为 `requirement_state_machine.py`，替换主/微状态、门禁表、init 字段（`--req-id`/`--title`/`--module`）、状态目录 `runtime/req/`、`worktree-set` 命名 `feature-<单号>`、commit 前缀 `feat:`；
3. 在 `hooks/AGENT.md` 追加需求开发铁律；
4. 建 `design-reviewer` agent；**复用 `code-reviewer`**（参数/路径改 requirement 版）+ 复用 `memory-gen`/`memory-push`；
5. 登记技能索引；
6. 用一条真实需求单跑通全流程（重点验证 §6.3 代码审查闭环的门禁证据校验），按 §5 铁律验收后回写本设计；
7. **（吸收 writing-skills）以 TDD 方式开发本 skill**：先设计压力场景观察 agent 无 skill 时的基线行为 → 再写 skill → 用真实需求单验证 agent 遵守 → 迭代堵洞至坚不可摧；SKILL.md 的 description 用 "Use when…" 规范（第三人称、只写触发条件、不概括工作流）。
