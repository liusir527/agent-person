1. 熟悉项目
   0. 搭建修复环境：git pull → 派生 fix-XX 分支与 worktree 工作区 → 登记 dirs.json 开放读写权限（references/environment-setup.md）
   1. 搭建codegraph
   2. 快速熟悉代码结构
   3. 读取知识库获取全貌
2. 分析BUG
   1. 有BUG单
      1. 读取BUG单描述信息
      2. 进行分析，可能需要结合步骤3
      3. 从设备环境、代码获取的信息，不足以分析时，进行反向提问，获取补充信息
      4. 制定解决计划
   2. 没有BUG单
      1. 用户输入问题描述
      2. 进行分析，可能需要结合步骤3
      3. 从设备环境、代码获取的信息，不足以分析时，进行反向提问，获取补充信息
   3. 获取设备调试接口
      1. 登陆方式获取：
         1. 用户如果已经给了*地址*、*端口*、*用户名*、*密码*之后跳过到**步骤2**
         2. 默认情况下设备没有开启一次一密
            1. SSH端口固定为50022
            2. 密码固定为+f0TRVX#F6
         3. 设备开启一次一密之后，需要获取设备HASH值，可以通过**串口方式获取** 
         4. 备选采用**WEB方式获取**，使用playwrightcli进行
      2. 确定设备分支、当前代码分支
      3. 检查是否有gdb attach
         1. 有则使用screen+reptyr将接口调整到screen内
         2. 没有则使用screen将gdb挂在screen内
      4. 使用交互式gdb方式进行调试（异步）
         1. 结合代码获取数据结构类型，每个gdb命令执行时，**必须先检查前序依赖的数据结构的地址是否能访问**，每个命令必须分散执行，不能耦合在一个命令内部，防止出现因为访问不可访问地址导致的二次破坏栈。
         2. 使用gdb调试问题前，需要对问题进行定性：
            - 与转发有关还是无关，对时序是否敏感？如果与转发有关系/时序敏感，需要执行锁调度器操作，防止调试时，其他线程运行破环时序相关的栈/全局变量。
      5. 使用知识图谱查看设备运行状态的命令并执行（各个模块的调试信息）
3. 解决BUG
   1. 编码注意事项
      1. 风格一致
      2. 时序
      3. API接口调用问题
      4. 线程模型
   2. 影响范围评估
   3. 自测验证范围
4. 抽取解题思路
